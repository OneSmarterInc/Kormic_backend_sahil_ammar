# PostgreSQL to SQLite Migration (No Destructive Steps)

The backend now defaults to SQLite for local/direct runs. PostgreSQL remains supported by setting `DB_ENGINE=postgresql`, so the existing database can be exported and kept as a rollback source.

## Important

- Do **not** drop, truncate, or overwrite the PostgreSQL database.
- Take a logical Django backup before creating/loading SQLite.
- `dumpdata` covers Django-managed application data. LangGraph checkpoint tables are separate non-Django tables; keep the original PostgreSQL database as the archive for those historical checkpoints.
- The new SQLite mode writes Django-managed application data to `db.sqlite3`. LangGraph's transient graph checkpoint state is process-local in SQLite mode; persisted Kormic chat/message rows remain in the Django database.

## Windows CMD migration

Run from the backend repository root.

### 1. Update code and install dependencies

```bat
git pull origin main
python -m pip install -r requirements.txt
if not exist backups mkdir backups
```

### 2. Export the existing PostgreSQL application data

Temporarily force the backend to read PostgreSQL:

```bat
set DB_ENGINE=postgresql
python manage.py check
python manage.py dumpdata --natural-foreign --natural-primary --exclude contenttypes --exclude auth.permission --indent 2 > backups\postgres-data.json
```

Optional row-count snapshot before migration:

```bat
python manage.py shell -c "from django.apps import apps; print({m._meta.label:m.objects.count() for m in apps.get_models() if m._meta.managed})" > backups\postgres-counts.txt
```

The PostgreSQL database is not modified by these commands.

### 3. Switch to SQLite

```bat
set DB_ENGINE=sqlite
set SQLITE_PATH=db.sqlite3
```

If an old local SQLite file already exists, back it up first:

```bat
if exist db.sqlite3 copy /Y db.sqlite3 backups\db-before-migration.sqlite3
if exist agent_checkpoints.sqlite3 copy /Y agent_checkpoints.sqlite3 backups\agent-checkpoints-before-migration.sqlite3
```

For a clean conversion target, remove only the local SQLite files after backing them up:

```bat
if exist db.sqlite3 del /F /Q db.sqlite3
```

This does **not** touch PostgreSQL.

### 4. Create the SQLite schema and load the exported data

```bat
python manage.py migrate
python manage.py loaddata backups\postgres-data.json
python manage.py check
```

### 5. Verify the migrated data

```bat
python manage.py shell -c "from django.apps import apps; print({m._meta.label:m.objects.count() for m in apps.get_models() if m._meta.managed})" > backups\sqlite-counts.txt
type backups\postgres-counts.txt
type backups\sqlite-counts.txt
```

Review the counts. Some Django-generated tables such as permissions/content-types are intentionally regenerated by `migrate`, so compare business/application tables rather than expecting every framework table to have identical counts.

You can also verify representative records:

```bat
python manage.py shell -c "from accounts.models import Account; print('accounts=', Account.objects.count()); print(list(Account.objects.values_list('email','role')[:10]))"
```

### 6. Make SQLite persistent in .env

Set these lines in `.env`:

```ini
DB_ENGINE=sqlite
SQLITE_PATH=db.sqlite3
```

Then start normally:

```bat
python manage.py runserver 127.0.0.1:8000
```

## Roll back to PostgreSQL

Nothing is deleted from PostgreSQL. To switch back:

```bat
set DB_ENGINE=postgresql
python manage.py check
python manage.py runserver 127.0.0.1:8000
```

Or set `DB_ENGINE=postgresql` in `.env`.

## Production note

SQLite is appropriate for local development, demos, and modest single-host workloads. Kormic's Docker/production architecture may still use PostgreSQL by setting `DB_ENGINE=postgresql`; this is the safer option for multiple Gunicorn/Celery workers and heavier concurrent write traffic.
